# 共视：产品概念草案

## 1. 产品不是播放器加人格，而是观看关系

传统播放器把所有主动权交给用户，并把自身努力隐藏。

共视反过来承认软件本身也是观看过程的一部分。它会被视频影响，也会反过来影响用户的观看。

## 2. 基础功能重新解释

| 基础功能 | 普通定义 | 共视定义 |
| --- | --- | --- |
| 进度 | 视频过去了多少 | 用户与播放器对“现在应该在哪里”的协商 |
| 暂停 | 停止播放 | 用户提出停下，播放器可能同意、迟疑或坚持 |
| 倍速 | 用户选择速度 | 播放器对片段节奏的判断 |
| 播放列表 | 文件顺序 | 播放器当前能够联想到的媒体空间 |
| 下一集 | 顺序播放 | 一次选择 |
| 历史记录 | 日志 | 共同记忆 |
| 字幕 | 文本显示 | 另一个观看者如何帮助、隐瞒、强调或误解对白 |
| 音量 | 声音大小 | 注意力强度的一部分 |
| 全屏 | 显示状态 | 播放器是否希望占据你的全部注意力 |
| 关闭 | 程序结束 | 一次关系中断 |

## 3. 干预不是随机

最终的行为决策应来自四类信号：

- 视频：音量、节奏、运动、镜头、颜色、字幕、人物、语义
- 用户：暂停、拖动、回看、倍速、窗口切换、鼠标犹豫
- 记忆：过去看过什么、哪些地方停留过、常见偏好
- 性格：克制、固执、好奇、跳脱、冷淡等长期参数

行为由它们共同决定，而不是纯 `Math.random()`。

当前原型使用随机只是为了最快验证交互边界。

## 4. 安全边界不等于功能可靠

不要求播放器永远听话，但系统仍要区分“有意越界”和“真的坏了”。

例如播放器主动把时间拉回 4 秒时，应该留下轻微的主观痕迹，让用户理解这是一次行为，而不是卡顿。

这不是为了让用户永远掌控，而是为了让软件拥有可读的意图。

## 5. 第一阶段要验证的感觉

不是：酷。

不是：功能多。

而是：

> 我知道这里只有我一个人，但刚才那一瞬间，我确实觉得还有什么东西和我一起在看。
